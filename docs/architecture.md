# معماری

پروژه فقط سه بخش کاربردی دارد:

```text
Users
Projects
Tasks
```

کد در سه ماژول نگهداری می‌شود:

```text
Identity   -> کاربران و ورود
Projects   -> پروژه‌ها و اعضای پروژه
Tasks      -> تسک‌های پروژه
```

## وابستگی‌ها

```text
Identity
   ↓
Projects
   ↓
Tasks
```

`Projects` برای انتخاب اعضا از User استفاده می‌کند و `Tasks` به Project وابسته است.

## دسترسی

Authorization عمداً ساده است:

- `users.is_admin = true`: دسترسی مدیریتی کامل
- کاربر عادی: فقط پروژه‌هایی که عضو آن‌هاست
- Task برای کاربر عادی فقط وقتی قابل مشاهده است که Task متعلق به یکی از پروژه‌های عضو شدهٔ او باشد

عضویت پروژه فقط در جدول `project_user` نگهداری می‌شود.

## مدل داده

```text
User N <-> N Project
Project 1 -> N Task
```

دسترسی Task مستقیماً از عضویت در Project به دست می‌آید.

## همزمانی چرخه پروژه و Task

برای جلوگیری از تکمیل پروژه در حالی که یک Task همزمان در حال ایجاد یا تغییر است، ترتیب قفل‌گذاری در تراکنش‌های مربوط به این invariant همیشه ثابت است:

1. ابتدا ردیف `projects` با `lockForUpdate` قفل می‌شود.
2. سپس، در صورت نیاز، ردیف `tasks` با `lockForUpdate` قفل می‌شود.
3. بررسی وضعیت پروژه و Task و تمام تغییرات آن‌ها در همان تراکنش انجام می‌شود.

تکمیل پروژه نیز پس از گرفتن قفل پروژه، نبودن Task غیرپایانی را بررسی و سپس وضعیت پروژه را تغییر می‌دهد.
